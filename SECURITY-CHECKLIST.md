## 0. 🔴 САМОЕ ГЛАВНОЕ: Firestore Security Rules — без них ничего из остального не работает

В самом коде (`DayEditor.js`, комментарий в конце файла) уже написано открытым текстом: "Настоящая защита от злоупотребления... возможна только через Security Rules на стороне сервера — тут её пока нет". Это касается почти всех пунктов ниже с пометкой 🟡 — приложение может проверять права ("мастер"/"не мастер", "это мой userId") только у СЕБЯ, в JS. Если правила на сервере (Firebase Console → Firestore Database → Rules) этого не проверяют — любой человек может обойти приложение целиком (например через curl/Postman с чужим Firebase Web API Key, который не секретный) и писать в базу напрямую.

**Что сделать:** пришлите мне текущие Firestore Rules (Firebase Console → Firestore Database → Rules, весь текст) — разберу и предложу конкретные правила под вашу структуру данных (`users/{uid}`, `profiles/{uid}`, `ratings/{uid}/days/{date}`, `leaderboardTotals/{period}/users/{uid}`, `exercises`, `exercises/{id}/selectedExercises` и т.д.). Это одна, но самая важная задача — с неё имеет смысл начать.

## 1. 🔴 Broken access control — админка "спрятана" только во фронтенде

`ProfileScreen.js` показывает кнопки "Управление упражнениями" и "Пересчитать рейтинг" только если `isMaster` (поле `role` в `users/{uid}`, см. `useUserRole.js`). Сама проверка честная (роль читается из базы, не хардкожена), но это ровно тот сценарий из поста: если Security Rules не запрещают ОБЫЧНОМУ пользователю писать в коллекцию `exercises`/`folders` напрямую — спрятанная кнопка ничего не остановит.

**Что сделать:** в правилах разрешить `write` в `exercises`/`folders` только когда `get(/databases/$(database)/documents/users/$(request.auth.uid)).data.role == 'master'`. Также запретить обычному пользователю самому менять поле `role` в своём документе `users/{uid}` (иначе можно самому себе выдать "мастера").

## 2. 🔴 Brute force / отсутствие 2FA

Входа с ограничением попыток и двухфакторной защиты в приложении сейчас нет. Firebase Auth сам по себе частично защищает (есть встроенная защита от подбора + вы уже включили "Email enumeration protection" в Settings → User actions), но:

- Firebase поддерживает многофакторную аутентификацию (SMS/TOTP) — можно добавить как ОПЦИЮ в профиле, не обязательную для всех сразу.
- Стоит также включить **App Check** (Firebase Console → App Check) — он не про пароли, а про то, что к вашей базе стучится именно ваше приложение, а не скрипт/бот. Это отдельная, довольно быстрая настройка, закрывает сразу несколько пунктов (brute force, злоупотребление API).

**Приоритет:** App Check — сделать в ближайшее время (несложно). 2FA — можно отложить, это не критично для приложения без денег на балансе (пока).

## 3. 🟡 Credential stuffing (переиспользование пароля с других сайтов)

Полностью защититься нельзя (это выбор пользователя), но можно:
- Включить более строгую **Password policy** (Firebase Console → Authentication → Settings → Password policy — этот пункт вы уже видели в списке настроек) — минимальная длина, требование цифр/спецсимволов.
- В будущем — та же MFA из пункта 2.

**Приоритет:** низкий, можно сделать заодно с пунктом 2.

## 5. 🟡 IDOR (чтение/запись чужих данных по id)

Проверил `workoutDays.js`, `ratings.js`, `profile.js`, `selectedExercises.js` — везде `userId` берётся из уже аутентифицированного `auth().currentUser.uid` (передаётся пропом сверху из `App.js`), нигде в UI нет места, где можно ввести ЧУЖОЙ userId и получить его данные. Но окончательная защита — опять же Security Rules (`request.auth.uid == userId` на каждый документ в `users/{userId}/...`, `ratings/{userId}/...` и т.д.) — без них теоретически можно достучаться до чужих данных напрямую, в обход приложения.

**Что сделать:** закрывается автоматически, когда разберём правила в пункте 0.

## 6. 🟢 SQL / NoSQL-инъекция — не актуально при текущей архитектуре

Firestore — не SQL, запросы идут через методы SDK (`.collection().doc().get()` и т.п.), а не через строки, куда можно подставить чужой код. Инъекции такого типа тут физически невозможны, пока вы не добавите свой backend с "сырыми" SQL-запросами, собранными из пользовательского ввода строками.

**Что сделать:** ничего сейчас. Просто держите в голове на будущее, если появится отдельный сервер с обычной SQL-базой.

## 7. 🔴 Форвард-лукинг: поддельный вебхук и приём "оплата прошла" — актуально для донатов

Сейчас в коде платежей/донатов нет вообще — этот пункт не про существующий баг, а про то, что нужно сделать ПРАВИЛЬНО сразу, когда будете добавлять донаты.

**Что делать при добавлении:**
- Никогда не давать приложению самому решать "оплата прошла" и сразу выдавать плюшку — клиент можно подделать.
- Подтверждение оплаты должно приходить на ваш сервер (Cloud Function) через вебхук платёжной системы, и там ОБЯЗАТЕЛЬНО проверяться подпись/секрет вебхука (у Stripe, ЮKassa, CloudPayments и т.п. это стандартная и обязательная часть настройки).
- Если это будут внутриигровые покупки — использовать Google Play Billing / RevenueCat, а не собственный обработчик карт (снимает почти весь груз ответственности за хранение платёжных данных).

**Приоритет:** делать вместе с реализацией донатов, не раньше.

## 12. 🟢 Race condition — уже неплохо защищено, но тоже упирается в правила

Проверил: недельный бонус (`weeklyBonus.js`) уже защищён транзакцией с "меткой" — повторно начислить нельзя, даже если запросов придёт много одновременно. Пересчёт рейтинга дня — тоже транзакция + защита от слишком частых повторов (то, что чинили несколько сообщений назад). Хорошо продумано.

Остаточный риск — тот же, что и везде: конечная защита от "отправил свои очки/баллы напрямую в базу, в обход математики приложения" — это опять Security Rules с валидацией диапазона значений (пункт 0).
