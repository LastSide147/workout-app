## 0. Что уже исправлено в коде

### 0.1 Release-сборка была подписана debug-ключом

В `android/app/build.gradle` строка `signingConfig signingConfigs.debug` в блоке `release` означала: если кто-то соберёт релизный APK/AAB локально (`./gradlew bundleRelease`), он подпишется тем же ключом, что и отладочная сборка — паролем `android`, который есть в интернете в открытом виде в тысячах репозиториев. Итог: теоретически кто угодно может подписать поддельное обновление вашим "релизным" ключом.

Я переписал конфигурацию так:

- если рядом лежит файл `android/keystore.properties` — release подписывается ключом из него;
- если файла нет — release временно падает на debug-ключ, чтобы локальная сборка не ломалась, но такой файл нельзя грузить в стор.

Как создать свой боевой ключ — шаг 1 в инструкции ниже.

### 0.2 Лишние permissions в AndroidManifest.xml

Было заявлено 3 разрешения, которые нигде в `src/` не используются (проверил — ни `FileSystem`, ни `MediaLibrary`, ни overlay-виджетов в коде нет):

- `SYSTEM_ALERT_WINDOW` — рисование поверх других приложений. Тянулось из debug-манифеста самого React Native (нужно только для меню разработчика в debug-сборке), но было прописано и для релиза.
- `READ_EXTERNAL_STORAGE` / `WRITE_EXTERNAL_STORAGE` — тянутся из `expo-file-system` (входит в Expo SDK как зависимость, хотя вы им не пользуетесь).

RuStore-модерация проверяет каждое разрешение на соответствие реальной функциональности приложения — необоснованный доступ либо требует объяснения в консоли, либо тормозит проверку. Я убрал все три через `tools:node="remove"` — это гарантированно исключает разрешение из итогового манифеста, даже если библиотека продолжит его декларировать.

Если в будущем добавите, например, экспорт статистики в файл или выбор аватарки из галереи — тогда `READ_EXTERNAL_STORAGE`/доступ к медиа вернётся, но уже осознанно и с формулировкой для модератора.

## 1. Сгенерировать боевой ключ подписи (сделать самому, вручную)

Это должны сделать вы сами на своём компьютере — приватный ключ не должен проходить через чужие среды выполнения (в том числе через меня). Файл ключа — это постоянный "паспорт" приложения: потеряете — не сможете выпускать обновления под тем же `applicationId`.

```bash
# Выполняется один раз, из папки android/app
cd android/app
keytool -genkeypair -v \
  -storetype PKCS12 \
  -keystore upset-release.keystore \
  -alias upset-key \
  -keyalg RSA -keysize 2048 \
  -validity 10000
```

`keytool` спросит пароль хранилища, пароль ключа (можно совпадающие) и данные о вас (страна/организация — можно ставить прочерк, это не проверяется). RuStore требует RSA-ключ не короче 2048 бит — команда выше это обеспечивает.

Дальше:

1. Скопируйте `android/keystore.properties.example` → `android/keystore.properties` (я уже добавил его в `.gitignore`, в репозиторий не попадёт).
2. Впишите туда реальные пароли и `storeFile=app/upset-release.keystore`.
3. **Сделайте резервную копию `upset-release.keystore` в надёжном месте** (не в git!) — облачное хранилище с 2FA, менеджер паролей и т.п. Без этого файла вы не сможете выпустить ни одного обновления.

### Если вы собираете через EAS Build (`eas build`), а не `gradlew` локально

У вас уже настроен `eas.json` — судя по нему, сборки идут через EAS. В этом случае EAS по умолчанию **сам генерирует и хранит боевой ключ в облаке**, локальный `debug.keystore` в этом процессе не участвует. Проверьте, что у вас реально так:

```bash
eas credentials
# → Android → production → Keystore: должен быть настоящий ключ, не debug
```

Если EAS уже управляет ключом — шаг с `keytool` выше всё равно стоит сделать (для защиты локальных сборок, если вдруг кто-то соберёт релиз через `gradlew` в обход EAS), но для публикации в RuStore вам, скорее всего, нужен именно AAB-файл, скачанный из EAS (`eas build --platform android --profile production` → ссылка на скачивание в конце).

**Важно:** для RuStore и Google Play (если планируете) в идеале использовать **один и тот же ключ подписи** — иначе пользователи, установившие приложение из одного стора, не смогут получить обновление через другой (Android не разрешает установить APK с другой подписью поверх существующего). Если ключ EAS уже используется для Google Play — для RuStore нужен либо тот же ключ (экспортируется из EAS: `eas credentials` → скачать), либо отдельный, но тогда это два независимых "потока" пользователей.

## 2. Требования RuStore к сборке (проверено по официальной документации)

| Требование | Ваш проект |
|---|---|
| Формат: APK или AAB | Есть `eas.json` профиль `production` → по умолчанию AAB |
| Подписан ключом RSA ≥ 2048 бит | Исправлено в п.0.1, осталось сгенерировать ключ (п.1) |
| targetSdkVersion ≥ 28 (Android 9+) | Expo 56 / React Native 0.85 — SDK, который они подтягивают, точно выше 28. Проверить точное число: `cd android && ./gradlew :app:properties \| grep -i sdk` |
| Наличие 64-битных библиotek (arm64-v8a) при нативном коде | `reactNativeArchitectures=armeabi-v7a,arm64-v8a,x86,x86_64` в `gradle.properties` — уже включает arm64-v8a |
| Размер файла ≤ 5 ГБ | Не проблема для этого приложения |
| versionCode увеличивается с каждой версией | Сейчас `versionCode 1` — для первой версии нормально, для каждой следующей не забывайте увеличивать |

## 3. Регистрация аккаунта разработчика в RuStore — точные шаги

Публиковать бесплатное приложение может **физическое лицо**, отдельного юрлица/ИП для этого не нужно (ИП понадобится, только если позже подключите платную монетизацию через платёжные инструменты RuStore — с 1 февраля 2026 физлицам и самозанятым это недоступно, но на публикацию бесплатного приложения это никак не влияет).

Пошагово (проверено по официальной документации RuStore):

1. Открыть [console.rustore.ru](https://console.rustore.ru/) в браузере.
2. Нажать **«В консоль»**.
3. Нажать **«Войти через VK ID»**.
4. Ввести номер телефона, привязанный к VK ID, либо создать новый VK ID-аккаунт тут же.
5. Нажать **«Продолжить»** → **«Продолжить с этим VK ID»**.
6. Выбрать тип аккаунта **«Физическое лицо»** → **«Продолжить»**.
7. Проверить, что данные (email и т.п.) подтянулись из VK ID корректно → нажать **«Подтвердить»**.
8. Всё — доступна работа в RuStore Консоли, можно переходить к загрузке приложения (раздел 7 ниже).

Никаких паспортных фото/селфи на этом этапе, по актуальной документации, не требуется — это могло быть нужно раньше или потребуется отдельно, если будете подключать выплаты/монетизацию. Контактные данные потом можно поменять в разделе **«Профиль»**.

## 4. Персональные данные, 152-ФЗ и политика конфиденциальности

Ваше приложение хранит email, профиль (год/месяц рождения, вес, страна, город), тренировки и рейтинги пользователей в Firestore (структура `users/{uid}`, `profiles/{uid}`, `ratings/{uid}/...` — см. `SECURITY-CHECKLIST.md`). Это значит, что по 152-ФЗ вы — **оператор персональных данных**: закон определяет оператора как любого, кто самостоятельно определяет цели и состав обрабатываемых данных, независимо от того, физлицо это, ИП или юрлицо. Разбор по пунктам:

### 4.1 Нужна ли постановка на учёт (уведомление Роскомнадзора)? Скорее всего — да

Раньше (до 1 сентября 2022 года) в ст. 22 152-ФЗ был список исключений, под который могла попасть обработка данных «для заключения и исполнения договора с субъектом» — многие разработчики на это ссылались, чтобы не подавать уведомление. **Этот и почти все остальные пункты исключений отменены** законом 266-ФЗ. Сейчас (проверил актуальную редакцию ст. 22 на КонсультантПлюс) без уведомления можно обрабатывать данные только в 3 случаях:

1. данные включены в государственные информационные системы для защиты безопасности государства;
2. обработка идёт **исключительно без средств автоматизации** (то есть на бумаге, без баз данных и серверов);
3. обработка в целях транспортной безопасности.

Ваш случай — Firestore, серверы, приложение — это автоматизированная обработка, значит ни один пункт не подходит. **Вывод: подавать уведомление нужно**, и это не зависит от того, что вы регистрируетесь как физлицо, а не ИП — закон не делает для физлиц исключения из этого правила (есть отдельное исключение для обработки «для личных и семейных нужд», но оно про обработку данных, скажем, своей семейной адресной книги, а не про сервис для сторонних пользователей).

**Что делать конкретно:**

1. Зайти на [pd.rkn.gov.ru](https://pd.rkn.gov.ru/) → раздел **«Реестр операторов»** → **«Электронные формы заявлений»** → **«Перейти к заполнению формы электронного уведомления»**.
2. Заполнить форму. Из того, что реально нужно будет указать по вашему приложению:
   - ФИО и адрес (как оператора — физлица);
   - цель обработки — например: «предоставление функционала мобильного приложения для учёта тренировок: регистрация, аутентификация, хранение статистики и рейтинга пользователей»;
   - категории субъектов — пользователи мобильного приложения;
   - категории данных — email, год/месяц рождения, вес, страна, город, данные о тренировках;
   - правовое основание — согласие субъекта персональных данных (принятие политики конфиденциальности при регистрации);
   - действия с данными — сбор, запись, хранение, использование, удаление;
   - способ обработки — с использованием средств автоматизации, с передачей по сети;
   - **сведения о трансграничной передаче — укажите, что она есть** (см. пункт 4.2 ниже, это важно не упустить).
3. Подать можно электронно на сайте (если получится оформить онлайн — потребуется вход через Госуслуги/подпись) либо распечатать и отнести в территориальное отделение Роскомнадзора по месту вашей регистрации.
4. Уведомление подаётся **до начала обработки** — то есть по-хорошему до того, как в приложении появится первый живой пользователь, а не после. Раз приложение уже используется — имеет смысл подать как можно скорее.
5. Госпошлины нет — рассмотрение уведомления бесплатно по закону.

Штраф за неподачу уведомления (ст. 13.11 ч.10 КоАП) для граждан — 5 000–10 000 ₽, для юрлиц — 100 000–300 000 ₽. Для физлица это не критично много, но обязанность реальная, а не формальность "для юрлиц".

### 4.2 Локализация данных — отдельное, более серьёзное требование

Это отдельный от уведомления вопрос: закон 242-ФЗ (внёс поправки в ст. 18 152-ФЗ, действует с 2015 года) требует, чтобы **запись, систематизация, накопление, хранение, уточнение и извлечение** персональных данных граждан РФ при сборе (в том числе через интернет) велись **с использованием баз данных, физически находящихся на территории России**. Формально закон разделяет два процесса: первичный сбор/хранение — обязательно в РФ; трансграничная передача/дублирование за рубеж после этого — отдельный вопрос (можно, но с соблюдением условий, см. 4.3). То есть нельзя писать данные сразу в зарубежную базу, а потом когда-нибудь синхронизировать в РФ — по букве закона правильный порядок обратный.

Firebase/Firestore в стандартной конфигурации — это серверы Google Cloud, физически **не** в России. Это касается email, профиля (год/месяц рождения, вес, город, страна) — то есть как раз тех данных, которые ваше приложение сейчас пишет прямо в Firestore.

**Конкретная ответственность (ст. 13.11 ч.8-9 КоАП РФ, точные цифры):**

| Кто | Первое нарушение | Повторное |
|---|---|---|
| Гражданин (ваш случай при регистрации как физлицо) | 30 000–50 000 ₽ | 50 000–100 000 ₽ |
| Должностное лицо | 100 000–200 000 ₽ | 500 000–800 000 ₽ |
| Юрлицо | 1 000 000–6 000 000 ₽ | 6 000 000–18 000 000 ₽ |

Как это обычно обнаруживают на практике: Роскомнадзор направляет оператору запрос — подтвердить, где физически расположена база данных (обычно это происходит по жалобе пользователя, либо в рамках плановых/тематических проверок отдельных категорий сервисов, а не автоматическим сканированием трафика). Если оператор не может подтвердить локализацию — открывается дело по ст. 13.11 ч.8. Показательный прецедент — блокировка LinkedIn в России в 2016 году именно за нарушение локализации.

**Что можно сделать технически**, если решите закрыть этот риск, а не просто принять его: держать email/профиль/тренировки в базе на сервере в РФ (Yandex Cloud, VK Cloud, Selectel и т.п.) как основное хранилище, а Firebase оставить, например, только для Crashlytics/App Check (это не персональные данные пользователя) или как вторичную копию. Это архитектурное изменение — не разовая правка кода, отдельно распишу шаги, если решите этим заняться.

**Честно про риск:** для небольшого некоммерческого приложения без миллионов пользователей вероятность целевой проверки RKN невысока (это не значит "невозможна" — просто на практике внимание Роскомнадзора обычно привлекают крупные сервисы, утечки данных или жалобы конкретных пользователей). Но это моя оценка правоприменительной практики, а не юридическая гарантия — окончательное решение "оставляю как есть / переношу данные в РФ" за вами, это вопрос вашего риск-аппетита.

### 4.3 Трансграничная передача — ещё один нюанс

Даже если закрыть локализацию (данные пишутся сначала в РФ), сам факт хранения копии на серверах Google (США) — это трансграничная передача персональных данных (ст. 12 152-ФЗ). Здесь есть деление стран на входящие в перечень государств с "адекватной защитой" (утверждается приказами Роскомнадзора, в основном страны — участники Конвенции Совета Европы №108) и остальные. США в этот перечень не входят. Для передачи данных в страну **не из перечня** закон по общему правилу требует **письменного согласия субъекта именно на трансграничную передачу** — это отдельное согласие от обычного "согласен с политикой конфиденциальности" чекбокса при регистрации, и обычная форма его сбора (чекбокс в приложении) может не считаться "письменной формой" в строгом смысле закона.

Это тонкость, которая обычно всплывает только вместе с проверкой по локализации (п. 4.2) — отдельно за одну только трансграничную передачу малые приложения на практике не проверяют, но раз уж разбираем все нюансы — вот он.

### 4.4 Варианты серверов в России — чем заменить/дополнить Firestore

Для сравнения — актуальный бесплатный лимит самого Firestore (тариф Spark, обновляется каждый день по тихоокеанскому времени):

| Ресурс | Бесплатно в Firestore (Spark) |
|---|---|
| Чтения документов | 50 000 / день |
| Записи документов | 20 000 / день |
| Удаления документов | 20 000 / день |
| Хранение данных | 1 ГиБ |
| Исходящий трафик | 10 ГиБ / месяц |

Для маленького приложения вроде вашего это с большим запасом (десятки активных пользователей точно уложатся). Именно поэтому Firestore и удобен — щедрый бесплатный лимит и приятный SDK. Прямого 1-в-1 клона в России нет, но есть три рабочих направления, они отличаются по тому, сколько придётся переписывать в коде:

**1. Yandex Cloud YDB (Serverless) — ближе всего по модели оплаты к Firestore**

Тоже serverless, тоже оплата за операции (а не за постоянно работающий сервер), тоже управляемый сервис — не нужно самому администрировать базу. Бесплатный лимит: **1 000 000 "единиц запроса" (RU) в месяц + 1 ГБ хранения**. Чтение тарифицируется блоками по 4 КБ = 1 RU, запись — блоками по 1 КБ = 2 RU (минимум 2 RU даже за маленькую запись). Оплата в рублях, российскими картами, без каких-либо проблем с международными платежами.

Минус: YDB — это не документная база 1-в-1 как Firestore, а гибрид (можно использовать как key-value/документо-подобную, либо как SQL-таблицы через YQL) — придётся переписать слой доступа к данным (`src/services/*.js` у вас сейчас работает через `@react-native-firebase/firestore`), а авторизацию (Firebase Auth) и push — тоже отдельно чем-то заменять, готового Auth "из коробки" в комплекте с YDB нет.

**2. Самостоятельный хостинг open-source аналога Firebase (Supabase / Appwrite / PocketBase) на российском VPS**

Это конкретно то направление, которое ближе всего по ощущениям к тому, что у вас уже есть, потому что такие проекты специально скопировали механику Firebase (авторизация + база + realtime-подписки + хранилище файлов в одном продукте):

- **Supabase** — база на PostgreSQL, есть Auth (email/пароль, соцсети), Realtime (аналог live-подписок Firestore), Storage, Row Level Security — это прямой концептуальный аналог ваших Firestore Security Rules, только в виде SQL-политик. Официальное облако Supabase — тоже не в РФ (США/ЕС), но Supabase **можно развернуть самому** (self-host, официальный Docker Compose) на любом российском сервере.
- **Appwrite** — похожая идея, тоже self-host через Docker, чуть более "из коробки" под мобильные приложения.
- **PocketBase** — самый лёгкий вариант: один исполняемый файл на Go + встроенная SQLite, поднимается за 5 минут на самом дешёвом VPS. Меньше возможностей масштабирования, чем у первых двух, но для приложения с некоммерческой, немассовой аудиторией — более чем достаточно.

Стоимость здесь — не "лимит операций", а обычная аренда сервера. **Уточнение к предыдущему ответу**: цифру ~450 ₽/мес я называл для лёгкого варианта (PocketBase/голый Postgres); официальный полный набор контейнеров Supabase (см. ниже, из чего он состоит) требовательнее — сама Supabase рекомендует от 4 ГБ RAM для комфортной работы, это уже тариф порядка **~1000 ₽/мес** у Timeweb Cloud (2 ядра, 4 ГБ RAM, 50 ГБ SSD). Всё равно фиксированная сумма независимо от нагрузки, просто чуть больше, чем я сказал раньше — поправляю, чтобы не вводить в заблуждение.

#### Как физически устроен self-host Supabase и где там подводные камни

Важно понимать: **Docker сам по себе никак не решает вопрос локализации** — это просто способ упаковки и запуска программ (контейнеры), ему всё равно, на каком физическом сервере он работает. Локализацию решает не Docker, а то, **какой конкретно сервер вы для этого арендуете**.

Как это выглядит по шагам:
1. Supabase как компания предоставляет своё **облако** (supabase.com) — это серверы на инфраструктуре AWS, физически в США/ЕС/Сингапуре. Если просто зарегистрироваться на сайте Supabase и создать там проект — данные снова окажутся за границей, ничего не изменится по сравнению с Firebase.
2. Но весь код Supabase — открытый (на GitHub), и его можно запустить **самому, на своём сервере**, вообще без участия компании Supabase. Технически: вы арендуете VPS у российского провайдера → ставите на него Docker → скачиваете официальный `docker-compose.yml` из репозитория Supabase → командой `docker compose up` поднимаете набор контейнеров: Postgres (сама база), GoTrue (Auth), PostgREST (авто-API поверх базы), Realtime (аналог live-подписок Firestore), Storage API (файлы), Kong (шлюз, через который клиент стучится ко всем остальным сервисам), Studio (админ-панель). Все они работают локально, на арендованном вами железе — компания Supabase к этому серверу не имеет доступа и не знает о его существовании, как WordPress не знает, кто и где установил его код к себе на сервер.
3. Все данные (в буквальном смысле — файлы базы Postgres) лежат на диске именно этого сервера. Где физически стоит этот сервер — там и лежат данные.

**Подводные камни, на которые реально стоит обратить внимание:**

- **Не всякий "российский" провайдер = сервер физически в России.** Проверил конкретно: у Timeweb Cloud, помимо дата-центров в Москве/Санкт-Петербурге/Новосибирске, есть площадки в Германии, Нидерландах и Казахстане; у Selectel — помимо российских городов, ещё Узбекистан, Казахстан, Кения. При заказе VPS нужно **явно выбрать российский регион/дата-центр**, а не полагаться на то, что компания зарегистрирована в РФ. У VK Cloud в этом смысле проще — у них всего одна локация, Москва, перепутать негде.
- **Бэкапы.** Если настроите автоматическое резервное копирование базы во внешнее объектное хранилище (частая практика) — убедитесь, что это хранилище тоже в РФ (например, S3-совместимое хранилище у Selectel/VK Cloud), а не случайно настроенный по дефолту AWS S3 за границей — иначе весь смысл переезда теряется на этапе бэкапа.
- **CDN/защита от DDoS перед сервером.** Многие по умолчанию ставят Cloudflare перед своим сервером — бесплатно, удобно, защищает от атак. Но трафик в этом случае физически проходит через узлы Cloudflare по всему миру (включая за пределами РФ) прежде чем попасть на ваш сервер. Это спорная зона (транзит — не то же самое, что хранение), но если хочется однозначности — лучше воспользоваться защитой от DDoS самого российского провайдера или обойтись без стороннего CDN.
- **Отправка email.** Supabase Auth для писем подтверждения регистрации/сброса пароля использует SMTP — если подключите зарубежный сервис рассылок (SendGrid, Mailgun и т.п.), email адреса пользователей на мгновение, но пройдут через зарубежный сервер. Проще подключить российский SMTP-сервис.
- **Обновления и бэкапы — теперь ваша забота.** В облаке Supabase патчи безопасности накатывает сама компания; при self-host обновлять версии контейнеров, следить за местом на диске и настраивать бэкапы придётся вам (или мне, если буду помогать администрировать).
- **Docker Hub** (откуда скачиваются образы контейнеров) физически в США — но это просто загрузка программного кода, а не обработка персональных данных пользователей, тут беспокоиться не о чем.
- Если оставите часть Firebase-сервисов (Crashlytics, App Check) — они по-прежнему шлют техническую информацию на серверы Google за границей. Это уже не персональные данные в чистом виде (скорее технические идентификаторы устройства), но если задача — закрыть локализацию полностью и строго, про этот хвост тоже не стоит забывать.

**3. Управляемая БД в Yandex Cloud / VK Cloud / Selectel (PostgreSQL/MongoDB) + свой backend**

Самый гибкий, но и самый трудозатратный вариант: берёте managed PostgreSQL или MongoDB у любого из этих провайдеров, и сами пишете небольшой backend (Node.js/Express или облачные функции), который будет обслуживать приложение вместо прямых вызовов Firestore из клиента. Даёт полный контроль, но требует больше кода и больше вашего времени на поддержку — не рекомендую для старта, если только не планируете сильно расширять функциональность в будущем.

**Мой ориентир для вашего случая:** вариант 2 (self-hosted Supabase на дешёвом РФ VPS) выглядит наиболее вменяемым — переносит меньше всего архитектурной боли (Auth + Realtime + Storage в одном месте, концепция Security Rules переносится почти дословно в RLS-политики), и стоит предсказуемо мало (сотни рублей в месяц). Но это моя рекомендация по общей логике, а не готовое решение — если решите переезжать, это отдельная задача с планом миграции данных и переписыванием `src/services/*`, могу расписать пошагово, когда будете готовы.

## 4а. Если параллельно захотите в Google Play — не помешает ли это RuStore/локализации

Нет конфликта. Google Play **никак не требует, где физически лежат ваши серверы** — их правила касаются только раскрытия того, какие данные вы собираете (Data safety форма) и наличия политики конфиденциальности, а не географии хостинга. Если перенесёте персональные данные на сервер в РФ ради 242-ФЗ — это же хранилище прекрасно обслуживает и Google Play, и RuStore одновременно. Единственное, что нужно будет актуализировать при переезде данных — саму политику конфиденциальности (где физически хранятся данные) и Data safety форму в Google Play Console.

Отдельный практический момент по самому Google Play (не про хранение данных, а про доступность стора для разработчиков из РФ): свежая информация (2026 год) —

- регистрация нового аккаунта разработчика Google Play из России пока доступна: нужны госпошлина $25, официальное удостоверение личности (паспорт) и документ, подтверждающий адрес;
- публиковать и обновлять **бесплатные** приложения можно;
- монетизация/платные приложения для аккаунтов, привязанных к России, заблокирована из-за санкций с 2022 года;
- практическая сложность — оплата $25 сбора: Visa/Mastercard, выпущенные российскими банками, для международных платежей не работают, нужна будет карта другого банка/страны или сервис-посредник.

Раз ваше приложение сейчас бесплатное — публикация в Google Play технически возможна, платить за это не придётся (кроме разового сбора за сам аккаунт разработчика).

## 4б. Что нужно сделать, чтобы "зарегистрироваться" — сводка всех действий

Смешиваются три разных регистрации, разделяю:

1. **RuStore (для публикации сейчас, бесплатно)** — только аккаунт физлица через VK ID, разобрано в разделе 3. ИП НЕ нужен.
2. **Роскомнадзор** — не регистрация аккаунта, а разовое уведомление об обработке персональных данных (раздел 4.1). Нужно вне зависимости от статуса физлицо/ИП.
3. **ИП** — нужен, только если а) захотите монетизацию через RuStore (донаты/платные подписки) или б) сами решите вести деятельность как ИП для порядка. Если сейчас планов на платежи нет — можно пропустить этот пункт полностью и вернуться к нему позже.

   Если всё же решите открыть ИП, шаги такие:
   - Подать форму Р21001 — удобнее всего через [Госуслуги](https://www.gosuslugi.ru/) или сервис ФНС «Государственная онлайн-регистрация бизнеса» (при электронной подаче с усиленной подписью — без госпошлины; при личной подаче в МФЦ — пошлина 800 ₽).
   - Указать код ОКВЭД **62.01** («Разработка компьютерного программного обеспечения») как основной.
   - В течение 30 дней после регистрации подать уведомление о переходе на **УСН** (упрощённую систему налогообложения) — иначе по умолчанию останетесь на общей системе с НДС и более сложной отчётностью.
   - Через 3 рабочих дня — готова запись в ЕГРИП (это и есть подтверждение регистрации).
   - Открыть расчётный счёт ИП в банке (нужен для получения выплат, в том числе от RuStore после подключения монетизации).
   - Дальше написать в поддержку RuStore (support@rustore.ru или через чат в консоли) с просьбой перевести существующий аккаунт из "Физическое лицо" в "ИП" — это делается через тех. поддержку, а не автоматически.
4. **Google Play (по желанию, отдельно)** — свой аккаунт разработчика, $25, паспорт + подтверждение адреса, см. раздел 4а. Никак не связан с регистрацией в RuStore или ИП.

## 5. 🟡 Важный риск: Firebase App Check (Play Integrity) на устройствах без Google Play

Из вашего `SECURITY-CHECKLIST.md` видно: App Check переведён в режим **Enforce** для Firestore, провайдер — `Play Integrity`. Это требует **Google Play Services** на устройстве пользователя.

RuStore исторически ориентирован в том числе на устройства **без** Google-сервисов (часть Huawei, некоторые китайские прошивки, "очищенные" от Google Android). На таких устройствах Play Integrity не сможет выдать токен → любой запрос к Firestore будет отклонён Enforce-режимом → пользователь просто не сможет пользоваться приложением, и это не будет выглядеть как явная ошибка (скорее "зависшая" загрузка данных).

Официальной Google-независимой альтернативы Play Integrity в `@react-native-firebase/app-check` для Android нет — это ограничение самого Firebase App Check, а не вашего кода.

Варианты (решать вам, это компромисс между безопасностью и охватом аудитории):

1. **Оставить как есть.** Риск может быть невысоким на практике в 2026 году — у большинства актуальных Android-устройств в РФ Google Play Services всё ещё установлены "из коробки", даже если сам Google Play Store недоступен. Проверить конкретно нельзя без данных о вашей аудитории.
2. **Временно ослабить Enforce до Monitoring** перед публикацией в RuStore, понаблюдать за процентом устройств без валидного App Check токена в Firebase Console, и решить осознанно.
3. **Протестировать вручную** на реальном устройстве без Google Play Services (или с отключённым Play Integrity) перед публикацией — самый надёжный способ увидеть, ломается что-то или нет.

Если решите тестировать или ослаблять Enforce — скажите, помогу с конкретными шагами в Firebase Console и в коде.

## 7. Пошаговая инструкция публикации

1. **Подготовить сборку**: `eas build --platform android --profile production` (или локально `./gradlew bundleRelease` из `android/`, если ключ из п.1 уже настроен) → получить `.aab`.
2. **Зарегистрироваться в RuStore Console** (раздел 3 выше), пройти идентификацию.
3. Открыть [console.rustore.ru](https://console.rustore.ru), вкладка **«Приложения»** → **«Добавить приложение»** → ввести название → **«Добавить»**.
4. Открыть созданное приложение → **«Загрузить новую версию»**.
5. Выбрать тип: **Universal** (телефон+планшет; TV не нужен для этого приложения).
6. Загрузить `.aab`-файл — дождаться этапа **Upload**, затем **Processing** (можно закрыть вкладку, обработка идёт в фоне; черновик хранится 14 дней, дальше — модерация или дозагрузка).
7. Заполнить **«Безопасность данных пользователей»** — какие категории данных собираются (email, данные профиля, статистика тренировок) и зачем.
8. Заполнить **«Информация о приложении»**: название, категория, возрастная категория, теги (до 5), краткое и полное описание (раздел 6 выше).
9. Указать **контакты разработчика** (email).
10. Загрузить **иконку 512×512** и **скриншоты** (раздел 6).
11. Указать ссылку на **политику конфиденциальности** (раздел 4).
12. Указать в **«Комментарии для модераторов»** тестовый логин/пароль для входа в приложение (если функциональность требует авторизации — а у вас требует, судя по Firebase Auth) — без этого модератор физически не сможет проверить приложение.
13. Нажать **«Отправить на модерацию»**.
14. Дождаться результата проверки (проверяют: стабильность работы, соответствие описанию, разрешения, отсутствие запрещённого контента — полный список в разделе App Review Guidelines).
